=========================================
Important caveat — data persistence:

The live deployment's database (SQLite) runs on a workaround (copying
the database file into Vercel's writable /tmp directory on each cold
start — see Technical_Debt_Plan.pdf, TD-08) that was needed to make
the live site functional at all. Without it, every data operation on
the live site returned a server error. This workaround makes the site
USABLE but /tmp is EPHEMERAL — data added during a demo/grading
session may not persist indefinitely and could reset on a Vercel cold
start. If this matters for grading, note this limitation rather than
assume it is a new bug; it is documented, known behaviour.

The admin passcode is stored in the same SQLite database, so if a cold
start resets it, the admin passcode reverts to whatever value is
baked into the committed prisma/dev.db file (currently the Admin
Password documented above, already hashed -- not a plaintext
default) -- not to any earlier value. If you change the admin passcode
live via Admin Settings and then a cold start occurs before that
change is committed to the repository, the live value will revert to
what's in the repository, same as the regular user passcode already
behaves.

Notes for the student before further submission:

1. Do not commit or publish the real GEMINI_API_KEY, Resend API key,
   or admin passcode. Confirm your deployment platform's environment
   variable settings are configured with your own keys, separate from
   any local .env.local file.

   Turso) to replace the /tmp workaround before relying on this
   deployment for real, durable data — see Technical_Debt_Plan.pdf,
   TD-08, for the full recommendation. This is especially important
   now that the admin passcode is stored in the database.

3. If the User Test Password or Admin Password above are changed after
   this document is finalised, update this section (or note the change

4. The "Demo Data Generator" feature has been removed from the
   application entirely — the system now comes pre-populated with a
   full working dataset automatically, with no manual trigger and no
   destructive reset capability exposed anywhere.

5. Role-based authorisation (SRS.pdf, AUTH-07/AUTH-08 -- supersedes the
   earlier AUTH-05, which stated no role separation existed) is now
   IMPLEMENTED as of 2026-08-14: a two-tier Shop Staff / Administrator
   system with a full audit trail. The requirements traceability
   matrix, Technical_Debt_Plan.pdf, and Testing_Report.pdf have all
   been updated accordingly.

6. Before this admin feature was ever committed to source control, a
